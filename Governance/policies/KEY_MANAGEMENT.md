# Key Management Policy

## Purpose

This policy defines the lifecycle of every cryptographic key TeachLink Mobile depends
on: how one is generated, where it is stored, who may reach it, when it is rotated, and
how it is revoked. A key that nobody can enumerate is a key nobody can rotate, and a key
that is never revoked stays useful to anyone who copied it. This document exists so
that the answer to "which keys does this project hold, and who owns each one?" is
written down rather than reconstructed from a build configuration.

## Scope

This policy covers all cryptographic keys, from creation to destruction, including:

- symmetric data-encryption keys generated on device for the encrypted feature cache,
  as in `src/utils/encryptedStorage.ts`;
- asymmetric keys and certificates used for app signing, submission, and update
  delivery, whose custody is detailed in the
  [App Signing Key Policy](../domains/APP_SIGNING_KEYS.md);
- TLS server certificates and any pinning material, under the
  [Certificate Management Policy](CERTIFICATE_MANAGEMENT.md);
- commit and tag signing keys, under the
  [Commit Signing Policy](COMMIT_SIGNING.md);
- keys issued to CI automation and third-party integrations, whose rotation cadence is
  set by the [Secret Rotation Policy](SECRET_ROTATION.md); and
- service-account keys, under the [Service Accounts Policy](SERVICE_ACCOUNTS.md).

This policy governs the **key**; the [Encryption Policy](ENCRYPTION.md) governs the
**algorithm**, and the two are read together because a key is only as strong as the
primitive protecting it.

## Key Inventory

Every key the project holds is listed with an owner. A key that exists and is not on
this list is unmanaged, and the first action is to find its owner or destroy it.

| Key group | Where it lives | Accountable owner | Lifecycle policy |
| --- | --- | --- | --- |
| iOS distribution certificate and private key | EAS credential store | [Release Manager](../roles/RELEASE_MANAGER.md) | [App Signing Keys](../domains/APP_SIGNING_KEYS.md) |
| iOS provisioning profile | EAS credential store | [Release Manager](../roles/RELEASE_MANAGER.md) | [Certificate Management](CERTIFICATE_MANAGEMENT.md) |
| App Store Connect API key (`.p8`) | EAS and secret store | [Release Manager](../roles/RELEASE_MANAGER.md) | [Secret Rotation](SECRET_ROTATION.md) |
| Android upload keystore (`.jks`) | EAS credential store | [Release Manager](../roles/RELEASE_MANAGER.md) | [App Signing Keys](../domains/APP_SIGNING_KEYS.md) |
| Google Play service-account key JSON | Secret store | [Security Officer](../roles/SECURITY_OFFICER.md) | [Service Accounts](SERVICE_ACCOUNTS.md) |
| Commit and tag signing keys | Each contributor's own device or hardware token | The signer, verified by the [Security Officer](../roles/SECURITY_OFFICER.md) | [Commit Signing](COMMIT_SIGNING.md) |
| On-device feature-cache data key | iOS Keychain / Android Keystore via `expo-secure-store` | Generated and destroyed on device; no human owner | This policy |
| CI and integration API tokens | GitHub Actions secrets, provider secret stores | [Security Officer](../roles/SECURITY_OFFICER.md) | [Secret Rotation](SECRET_ROTATION.md) |

Recording a new key group is part of creating it. A key introduced by a change lands in
this table, or in the register the policy it belongs to, in that same change.

## Key Generation

- Keys are generated by a cryptographically secure random number generator, never by a
  general-purpose one. `encryptedStorage.ts` generates its AES key with `expo-crypto`;
  a change that substitutes `Math.random()` is a defect.
- Key length and algorithm follow the
  [approved algorithms](ENCRYPTION.md#approved-algorithms): AES-GCM 256 for symmetric
  data keys, RSA at 2048 bits or above or ECDSA P-256 and above for asymmetric keys.
- A key is not generated from a passphrase-derived value unless a KDF per the approved
  list is applied. Deriving a key from a password with a bare hash is not permitted.
- Each key has a purpose. A key used for two purposes must be split, because the
  compromise of a shared key compromises both uses at once.
- Keys are generated as late as possible and destroyed as early as possible. An
  on-device cache key is created when the feature first needs it rather than at install
  time.

## Storage and Access Rules

| Rule | Detail |
| --- | --- |
| Never in the repository | No key, private half, keystore password, or passphrase is committed, including in examples, tests, fixtures, and screenshots |
| Approved stores only | Protected storage (`expo-secure-store`, i.e. Keychain and Android Keystore), the EAS credential store, or the platform secret store |
| Never beside the ciphertext | A data key is not stored in the same place as the data it protects. The feature-cache key lives in protected storage while the ciphertext lives in `AsyncStorage` |
| Narrow scope | A key is scoped to the single store, workflow, or environment that needs it |
| Individual custody | Private keys are personal and non-transferable; a shared key defeats attribution and is not permitted |
| No sharing | A private key is never pasted into an issue, pull request, chat, or log |
| Least privilege for access | Only the named owner can export or replace a key; contributors and reviewers may request a build but may not read or copy key material |
| Minimum exposure | A key is never held in memory longer than the operation requires, and never written to a crash report or telemetry event |
| Backup exclusion | Stored key material is excluded from device backup, so a restored device cannot resurrect a session or key |

Where a decision requires a judgement about who should hold a key, the
[Decision Rights Matrix](../matrices/DECISION_RIGHTS_MATRIX.md) resolves it.

## Rotation

Rotation replaces a key with a new one before the old one becomes a liability, on the
cadence set by the policy that owns the key:

| Key group | Cadence | Rotation policy |
| --- | --- | --- |
| Signing and submission material | At minimum annually | [App Signing Key Policy](../domains/APP_SIGNING_KEYS.md#rotation-process) |
| Platform tokens and service-account keys | 90 days | [Secret Rotation Policy](SECRET_ROTATION.md) |
| Third-party and CI integration keys | 180 days | [Secret Rotation Policy](SECRET_ROTATION.md) |
| Commit signing keys | On expiry or suspicion of compromise | [Commit Signing Policy](COMMIT_SIGNING.md#rotation-expiry-and-revocation) |
| On-device feature-cache keys | On compromise signal, or when the protected storage is reset | This policy |

Rotation is immediate, regardless of schedule, when a key is suspected or confirmed
exposed, when a holder leaves the team or loses the device holding it, or when there is
evidence of an unauthorised build, upload, or use.

Order of operations matters. Revoke or retire the old key at the source **before**
returning to service, then verify the new key works. For signing material the
superseded key is retained in the secure store only until the store accepts a build
signed with the new key, which is the rollback position described in the
[App Signing Key Policy](../domains/APP_SIGNING_KEYS.md#rotation-process).

Previously signed artefacts stay valid. History is not rewritten to re-sign commits or
re-issue builds that users already have; the affected window is reviewed instead.

## Revocation

Revocation is the action that actually removes trust, and replacing a secret without
revoking it leaves the old value usable.

- Revocation happens **at the source**: the certificate is revoked, the token is
  deleted, the keystore is disabled, or the signing key is removed from the account.
  Overwriting a stored value is not revocation.
- Revocation is recorded. The revoked key identifier, the date, the reason, and the
  person who performed it are written to the relevant register or issue, so a later
  reader can tell a deliberate revocation from a lost record.
- Revoked keys are never deleted from the inventory. They are marked revoked, with the
  date, because the record of what was trusted is part of the audit trail.
- A revoked key that is later found in use indicates a compromise, not a mistake, and
  is handled as an incident through the [Security Policy](../SECURITY_POLICY.md) and
  recorded in the [Incident Log](../registers/INCIDENT_LOG.md).
- Revocation is complete when the key can no longer authenticate or validate anything.
  A key that is revoked but still present in a cached build configuration is not
  revoked.

## Destruction

A retired key is destroyed once the retention requirement is met and no build, tag, or
commit still depends on it. Destruction means the key material is no longer
recoverable from the store, from backups, and from the devices of anyone who held it.
On a user's device, destroying the protected-storage entry destroys the data it
protects, which is why the feature cache is designed to be re-fetchable rather than
irreplaceable.

## Verification

Key controls are verified rather than assumed:

| Verification | How |
| --- | --- |
| A key is reachable only by its owner | The [Access Register](../registers/ACCESS_REGISTER.md) entry matches the exportable set |
| A key is not in the repository | `.gitignore` covers the key file types, and the ignore-rule audit in the [App Signing Key Policy](../domains/APP_SIGNING_KEYS.md#enforcement-checks) runs before a release |
| A rotation worked | The new key authenticates and the old one is verifiably rejected at the source, per the [Secret Rotation Policy](SECRET_ROTATION.md#verification-requirement) |
| A revocation worked | An attempt to use the revoked key fails, and the result is recorded |
| A key is in inventory | Each key group in the inventory table has an owner who confirms it still exists |

## Enforcement Status

- Key custody is enforced by platform storage guarantees, `.gitignore` rules, review of
  diffs touching `eas.json`, `app.config.ts`, and `.github/workflows/`, and the
  pre-release ignore-rule audit. No automated check inspects a key store.
- Key rotation age is not machine-checked. Cadences are tracked on the calendar the
  [Secret Rotation Policy](SECRET_ROTATION.md#scheduling-and-reminders) describes.
- The inventory above is a maintained document; it is only useful if it is corrected
  when a key group changes.

## Exceptions

A deviation — an unrotated key past its cadence, a key stored outside an approved
store, or shared custody — is recorded in the
[Exception and Waiver Register](../registers/EXCEPTION_REGISTER.md) with an approver
holding the authority to grant it, the compensating control, and an expiry no more than
12 months ahead. Where children's data is involved, the
[Children's Data Policy](../compliance/CHILDRENS_DATA.md) applies.

## Ownership and Review

The Security Officer owns this policy with the release-management team, who hold the
material. It is reviewed whenever a key group is added or removed, when a provider
changes its key model, and at least once every 12 months. Changes are proposed in a
pull request that touches only the `Governance/` folder.
